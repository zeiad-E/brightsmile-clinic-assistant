BrightSmile: how it works, in 10 diagrams

Start at 01 and go down: each diagram zooms in on one part of the one before it. All 10 were drawn from the code at commit 84a7b06 (10 Nov 2026). Each box lists the source files and lines it was drawn from.

The big picture

  1. 01System overviewarchitecture Every running piece: browser → Next.js on Vercel (/api rewrite) → Express on Render (plus the private LLM engine) → Supabase, Brevo, GitHub, keep-warm.
  2. 02Backend layersarchitecture One request's path through the backend: middleware → 7 routers (113 endpoints) → controllers → services → models → Postgres.

How people get in

  1. 03Sign-in and request authsequence Emailed-code sign-in, the 15-minute JWT and the refresh cookie, the checks on every request (token → session → permission), refresh and sign-out.

The patient assistant

  1. 04The assistant: its partsarchitecture Chat API, capacity gates, agent loop, reviewer AI, tool sandbox, knowledge and memory, team take-over, and what each one saves.
  2. 05One chat turn, step by stepworkflow From one message to the reply: early checks, masking, AI + tools (up to 8 rounds), the reply checks and reviewer, the retry, and the fixed-reply and handover paths.
  3. 06Booking: propose, then confirmsequence Why a chat booking takes two messages: propose_booking saves it as pending, and the patient's "yes" then runs confirm_pending_action → book_appointment.

Work that runs on its own

  1. 07Background jobsdataflow What puts work in the jobs table, the 30-second runner, and the handlers: chat summaries, knowledge ingest, waitlist emails, reminders, the nightly clean-up.

The database

  1. 08Database: all 27 tablesERD Every table and every column, grouped by area (clinic setup, bookings, people, assistant chats, assistant knowledge, system), with the main links.
  2. 09Database functionsarchitecture The 20 database functions and triggers: which backend code calls each one, and which tables and views it touches.

The website

  1. 10Frontend page maptree Every page under /en and /ar: public site, patient /account, team /dashboard and owner /owner, and who can open each.

Notes

Folders: each diagram has its own numbered folder. Inside it, candidate.json is the source you edit and the .html file is what you open. The other files are check receipts.

Updating one: edit its candidate.json, then run archify's finalize again with --repo-root . and a new commit in meta.repository.revision.

Old versions: the diagrams from October are in _archive/ and are out of date. You can delete that folder.
